# Архитектура

Гранка — локальный HTTP-сервер и браузерный редактор. Внешние сервисы
используются только при запуске соответствующей команды пользователем.

| Модуль | Ответственность |
|---|---|
| `config.py` | Пути, порт, рабочие папки и интеграции |
| `document_store.py` | Ревизии, валидация и атомарные записи |
| `text_edit.py` | Неизменяемые версии и перенос пометок |
| `editorial_workflow.py` | Решения автора и проверка цитат |
| `editorial_requests.py` | Поручения и вопросы автору |
| `author_preferences.py` | Личные правила, история решений и проверочный набор |
| `rule_learning.py` | Предложения правил с основаниями, принятие и отключение |
| `batch_decisions.py` | Атомарные пакетные решения и отмена |
| `jobs.py` | Фоновые задания и квитанции |
| `ai_provider.py` | Codex и OpenRouter, сохранение ответов до проверки |
| `iimeter.py` | Сравнение с личным корпусом |
| `deep_analysis.py` | Карта статьи, диагноз и перепроверка связанных замечаний |
| `text_signals.py` | Ограниченные локальные подсказки повторов и серийной подачи с точными позициями |
| `telegram.py` | Бот, предпросмотр и журнал отправок |
| `site_publish.py` | Снимки, Git и порядок контуров |
| `site_wordpress.py` | Настраиваемый SSH/WP-CLI |
| `site_engine.py` | Рендер Markdown и операции WordPress |
| `publication_plan.py` | Личный календарь, распределение дат и квитанции опубликованных статей |
| `planning_library.py` | Чтение Markdown и разметки для календаря, этапы готовности |
| `blatero_export.py` | Локальный снимок календаря для доски Blatero без изменения статей и публикаций |
| `library_locations.py` | Выбранные пользователем папки и отдельные файлы, локальное хранение с ревизией |
| `file_dialog.py` | Системный выбор источника в отдельном процессе; ручной путь при отсутствии Tk |

Сервер связывает модули с HTTP. Клиент разделён на ES-модули в `static/ui/`.
`markdown-view.js` сопоставляет оформленные блоки с исходником: при правке
пересобираются затронутые блоки, остальные сохраняются дословно.

## Сохранность

`planning.publications` связывает исходник (root + относительный путь разметки)
с проверенными URL и датой без записи в Markdown. Библиотека объединяет
подтверждённые копии по адресу публикации; календарь использует те же источники,
сохраняя ID и заметки при переходе в опубликованное состояние. Квитанции
продакшена остаются приоритетным подтверждением. Опубликованные записи
календаря без файла представлены внешними ссылками в библиотеке.

Переход `?root=...&source_file=...` проверяет точное совпадение с исходником
или раскрываемой копией в текущем каталоге библиотеки. Только найденный
источник открывается через общий `openSource`; для Markdown без разметки
выполняется штатное создание `.granka.json`. Поиск по названию не участвует
в выборе файла. Отсутствующий источник не открывает другую статью.

Мутации передают `expected_revision` и `operation_id`. Сервер проверяет
ревизию, применяет операцию, валидирует результат и атомарно заменяет файл.
Позиции пометок считаются в символах Unicode. Старые версии неизменяемы.

Обложка — поле `versions[].cover` с относительным `src` и `alt`.
Анонс хранится в `announcement`. Генерация возвращает варианты; применение
и публикация требуют действия пользователя.

Задания работают со снимком. Конфликт не затирает свежую редакцию.
Telegram сохраняет пост до отправки и не повторяет неоднозначный запрос.
WordPress сверяет текущую страницу перед записью; каждый контур имеет квитанцию.

Задание `deep-analysis` выполняет до трёх последовательных запросов: `map`,
`diagnose`, `verify`. В каждый входят исходный текст, защищённые позиции,
комментарии и личные правила; диагноз получает карту, перепроверка — кандидатов.
Директории этапов сохраняют промпты, сырые ответы и квитанции провайдера.
Отказ этапа останавливает цепочку без повтора и без частичной записи в статью.
`progress.json` отражает текущий этап в баннере задания.

Перед диагнозом вычисляются локальные подсказки: лексическое сходство
предложений (до 400 предложений), совпадающие начала абзацев, серии оговорок
и коротких блоков. Слова кода и адреса не участвуют в сравнении, цитируемые блоки пропускаются; исходные позиции
сохраняются. До 14 групп с 2–6 цитатами передаются диагнозу и перепроверке
как ориентиры для чтения. Они не создают замечаний, оценок или авторских решений.
Суммарная длина цитат подсказок ограничена 12000 символов.
Перепроверка должна оспаривать и карту первого прохода. Само наличие поля
coverage не является доказательством, что модель заметила все проблемы.

`deep_analyses[]` — отдельные отчёты с версией и SHA256 текста, картой,
пятью направлениями проверки, несколькими цитатами у каждого замечания,
контраргументами, решениями перепроверки и автора. Это не `annotations`:
пересечения с обычными пометками допустимы, применение замен их не использует.
У цитаты есть точный `quote`, нулевой `occurrence`, Unicode-позиции и роль
`revise`/`context`. Защищённые и отклонённые автором формулировки допускаются
только как контекст; повтор требует хотя бы двух разных позиций.
Все кандидаты должны получить ровно один вердикт; неизвестный или пропущенный
идентификатор останавливает задание. Неверные цитаты отбрасываются с видимой
причиной. Смена версии не переносит глубокие замечания на новые позиции.

Неверные блоки карты пропускаются с предупреждением, пока остаётся хотя бы один
проверенный блок; порядок исправляется по исходным позициям. Превышение лимита
описательных полей сокращается с видимым уведомлением, сырые ответы сохраняются
полностью. Пропуск направления проверки, неизвестный или отсутствующий вердикт
по кандидату остаются ошибкой неполного разбора, без автоматического повтора.

`/api/deep-decision` использует общую ревизионную мутацию; решения consider,
dismiss и addressed не меняют Markdown. Последние 20 решений этой статьи
передаются следующему разбору с указанием версии. Старые отчёты остаются
доступны для чтения, независимо от будущих изменений личных правил.

Календарь хранится в `publication-plan.json` личного каталога данных.
Черновики проецируются из рабочих папок без изменения Markdown и создания
разметки. Появление разметки сохраняет идентификатор карточки. Личные даты,
оценки и исключения перекрывают проекцию, актуальность текста и результаты
проверок читаются из источника. Ревизия календаря включает редакцию исходника.
Предпросмотр распределения ничего не записывает; применение повторно проверяет
ревизию и рассчитывает тот же план. Уже назначенные даты занимают места
в расписании. Подтверждённые публикации сайта проецируются из квитанций;
их нельзя переименовать или перенести как обычную идею. Календарь не вызывает
провайдеров, WordPress или Telegram и не является фоновым планировщиком отправок.

## Конфигурация и приватность

Перед анализом личные правила читаются из `corrections_file`, решения — из
настроенных рабочих корней. Цепочки `source_annotation` исключают дубли
между версиями; в промпт входят только подходящие примеры без путей источников.
В квитанции анализа сохраняются отпечаток предпочтений и число использованных
правил/примеров. `rule_id` и `rule_title` позволяют группировать новые карточки.

Пакет проходит одну ревизионную мутацию; неверная карточка отменяет всю операцию.
Проверочный набор и отчёты живут в `author-preferences` личного каталога данных.
Задание `benchmark` возвращает отчёт и не изменяет статью.

Задание `rules` сохраняет предложения в личном каталоге `suggestions`.
При принятии проверяются ссылки на авторские решения и ревизия правил.
Принятые правила и исключения хранятся отдельно в `managed-rules.json`;
файл исходных предпочтений остаётся неизменным. Уточнение содержит ссылку
на предыдущее правило. Отключение восстанавливает его, внешнее изменение
исходника помечает зависимое уточнение устаревшим. Проверка модели фиксирует
отпечаток правил, действовавших при формировании запроса.

В поставке нет пользовательских статей, корпуса, токенов, адресов рабочих
серверов и учётных данных. Defaults используют системный каталог данных
и переопределяются локальным JSON. Смена папок, порта и SSH-маршрутов
требует перезапуска.

Настройки управляются владельцем компьютера. Их нельзя принимать из
скачанной статьи или недоверенного проекта. Сервер слушает loopback,
проверяет Host, токен мутации, размер и формат запроса.

Движок сайта не зависит от соседнего проекта. Git использует авторство
пользователя. Сервисные адреса провайдеров — часть протокола; личные
endpoints и пути задаются конфигурацией.

## Выпуски

Windows-поставка содержит папки `app`, `runtime`, `codex` и маленький WinExe
launcher. Он запускает `start-granka.py` встроенным `pythonw.exe`. Этот вход
переносит конфигурацию в личный каталог состояния до импорта серверных модулей;
исходный запуск через `launch-granka.py` сохраняет прежние настройки.
Официальный переносимый Python включает Tk, зависимости устанавливаются из
закреплённых wheels без pip на машине пользователя. `._pth`-изоляция runtime
исключает системные Python-пакеты и PYTHONPATH.

Демо копируется один раз только в пустой каталог по умолчанию. Явные корни
и существующие статьи не подменяются. Идентичность сервера сверяется перед
повторным запуском и остановкой; активное задание блокирует остановку.
Mutex установленной копии защищает обновление/удаление от замены занятых
файлов. Inno Setup не удаляет состояние и не меняет системный PATH.

`tools/windows/build.py` проверяет явный список исходников, SHA256 загрузок
и автономные импорты. Скрипт собирает установщик и ZIP, сохраняет манифест и
контрольные суммы. `tools/windows/smoke.py` проверяет настоящий launcher,
редактирование в браузере, историю, повторный запуск и остановку в отдельном
состоянии с убранными системными инструментами из PATH. Вход в настоящий
аккаунт и запуск платных запросов в эти проверки не входят.

`VERSION` — источник номера приложения. CHANGELOG и DEVLOG описывают
изменения и решения. `tools/release.py` проверяет согласованность и создаёт
неперемещаемый тег. Публичная поставка проходит `tools/public_audit.py`;
экспорт не переносит Git-историю и личные файлы.
